# Audit di Sicurezza, Privacy e Qualità
## Gestionale Buoni Mensa — San Lorenzo del Vallo
**Data:** 8 ottobre 2026  
**Revisore:** Cloud Agent (Cursor)  
**Ambito:** Codice, infrastruttura, GDPR, sicurezza, accessibilità

---

## Sintesi Esecutiva

Il sistema gestionale per i buoni mensa presenta **vulnerabilità critiche in materia di privacy e GDPR** dovute alla **pubblicità del repository GitHub**, che contiene dati personali e sensibili (codici fiscali, nomi di minori, informazioni sanitarie implicate dalle allergie/diete) visibili pubblicamente nella cronologia git. L'autenticazione tramite password condivisa presenta rischi elevati. Sono state rilevate 9 vulnerabilità di sicurezza nelle dipendenze, assenza di header HTTP di sicurezza, e problemi di accessibilità. L'applicazione funziona correttamente dal punto di vista funzionale, ma richiede interventi urgenti per la conformità al GDPR.

   - Esecuzione di `npm audit --json`.

5. **Test manuale in ambiente locale:**
   - Creazione di `.env.local` con password di test.
   - Build e avvio server produzione locale (`npm start`).
   - Verifica redirect `/` → `/accesso` per utenti non autenticati.

   - Verifica protezione API: tutte le route API richiedono autenticazione. ✅
   - Verifica esposizione file sensibili: `.env`, `data/mensa.sqlite`, `package.json` non accessibili (redirect a login). ✅
   - Verifica TLS: HTTPS attivo, certificato valido. ✅

7. **Verifica GDPR:**
   - Controllo presenza informativa privacy: **assente**.
   - Controllo base giuridica documentata: **assente**.
   - Controllo DPIA: **assente**.
   - Controllo accordi con responsabili (Turso, Vercel): **non documentati**.
   - Controllo procedura diritti interessati: **assente**.

   - Il repository GitHub è **pubblico**: https://github.com/vincenzocuria/gestionale-buoni-mensa
   - Lo schema del database, il README e i commenti nel codice rivelano che il sistema tratta codici fiscali, nomi, cognomi di minori, e informazioni su tariffe ridotte (potenzialmente ISEE/dati economici).

### Attività Svolte (Inferite da Analisi Codice)

1. **Analisi del flusso autenticazione:**
   - Password condivisa, hashing SHA-256 per token sessione, cookie httpOnly con `sameSite: lax`.
   - Nessun audit trail per tracking operatori.

2. **Analisi gestione dati personali:**
   - Codici fiscali, nomi, cognomi salvati in chiaro in DB.
   - Export Excel/PDF includono tutti i dati personali.
   - Nessuna crittografia a riposo dei dati sensibili.

3. **Analisi superficie di attacco:**
   - Tutte le API protette da autenticazione (positivo).
   - Nessun endpoint esposto pubblicamente.
   - Cookie di sessione con flag `secure` in produzione.

4. **Analisi accessibilità e UX:**
   - Nessun test automatico WCAG eseguito (richiederebbe browser headless).
   - Codice usa componenti semantici HTML (`<button>`, `<table>`, ruoli ARIA presenti in alcuni componenti).
   - Responsive: classi Tailwind per mobile (`md:hidden`, `md:block`).

## Valutazione: Il Repository Deve Essere Privato?

**SÌ, IMMEDIATAMENTE.**

### Motivazioni

1. **Obblighi GDPR:**
   - Il repository contiene lo schema di dati personali (codici fiscali, nomi di minori, dati sanitari impliciti).
   - Rendere pubblici questi schemi, anche senza dati reali, espone:
     - Quali informazioni sono raccolte.
     - Come sono strutturate.
     - Potenziali vettori di attacco.
   - Il Principio di "Privacy by Design" (art. 25 GDPR) impone di minimizzare l'esposizione.

2. **Sicurezza:**
   - Un attaccante può studiare la logica di autenticazione (`lib/auth`), i flussi API, e identificare vulnerabilità (anche se nessun segreto è esposto).
   - La pubblicità del codice facilita attacchi mirati (social engineering su operatori del Comune, phishing che replica l'UI, ecc.).

3. **Compliance:**
   - Un repository pubblico per un sistema che tratta dati di minori in ambito PA non è giustificabile, nemmeno come "trasparenza" amministrativa.
   - Se il Garante Privacy italiano dovesse effettuare un'ispezione, questo potrebbe essere considerato una misura di sicurezza inadeguata.

**Alternativa (solo se richiesto per trasparenza PA):**
- Pubblicare una versione "sanitized" del codice (senza riferimenti specifici a Turso, Vercel, nomi di servizi, schemi DB completi) su un altro repository pubblico, con disclaimer che non contiene configurazioni reali.
- Mantenere il repository operativo privato.

## Conclusioni

Il sistema **funziona correttamente** dal punto di vista applicativo e presenta buone pratiche di sicurezza a livello di codice (es. protezione API, sanitizzazione input, transazioni DB). Tuttavia, **presenta rischi critici sul piano della privacy e conformità GDPR**, principalmente per:

1. La **pubblicità del repository GitHub**.
2. L'**assenza di documentazione e misure organizzative GDPR** (informativa, DPIA, ROPA, procedure diritti, accordi con responsabili).
3. L'**autenticazione tramite password condivisa**, che impedisce audit trail individuali e facilita compromissioni.

Le **vulnerabilità di sicurezza nelle dipendenze** e l'**assenza di header HTTP di sicurezza** sono risolvibili rapidamente e non costituiscono rischi immediati allo stato attuale (essendo devDependencies e considerando che l'app è già protetta da autenticazione), ma devono essere corrette per buona prassi.

Si raccomanda di affrontare **con urgenza** i rilievi di severità Critica e Alta, in particolare quelli GDPR, e di coinvolgere un consulente legale specializzato in protezione dati.
